# yt-scribe — design

Date: 2026-08-02

## Problem

A video cannot be skimmed. A feed reader shows you a title and a thumbnail and
asks you to spend twenty minutes finding out whether the video was worth it.
Text sources do not have this problem: you read the first sentence and move on.

The fix is to turn the audio into text before it reaches the reader. Nothing
self-hosted does this today.

## Why this is not already solved

Measured while trying to solve it with existing tools, 2026-08-01/02:

- **Karakeep** archives bookmarks, crawls pages, searches, and summarises with a
  local LLM — but a YouTube link crawls to its description and nothing more.
  [Issue #1629](https://github.com/karakeep-app/karakeep/issues/1629), open since
  2025-06, asks for transcription; a comment on it reads "There is currently no
  self-hosted app that does this."
- **oksskolten** extracts full text well, translates and summarises against a
  local Ollama, and has a genuinely skimmable reading UI. Its README states it
  does not handle YouTube. Opening a video in it shows "コンテンツがありません" —
  summary and translation have nothing to act on.
- **RSSHub** has a provider-per-source architecture and even built-in LLM
  post-processing (`?chatgpt=1` against any OpenAI-compatible endpoint), but its
  routes are request-response. Transcription measured at 40s per video cannot
  happen inside a feed request, and RSSHub has no YouTube search route either.
- **YouTube's own captions** are not a substitute. On the same Japanese video the
  auto-caption gave 1,951 characters against whisper's 4,436, and corrupted
  meaning: 「ちょっと作り直しの第1回目」 came out as 「8ぞと作り直しの大外目」.
  Caption fetches also returned HTTP 429.

The gap is narrow and specific: something that produces the text, asynchronously,
and hands it to whatever reader the user already likes.

## Scope

Turn a list of YouTube channels into one Atom feed whose entries carry the
transcript, so any feed reader can treat video as an ordinary article.

**Not in scope**: a reading UI, a database to curate, search, tagging,
recommendation, or any integration with a specific reader. Those exist and are
better than anything this project would grow. The output is a feed; the reader
is the user's choice.

## Architecture

One batch process, run by a timer. No daemon, no queue, no message bus.

```
channel list ──▶ sources ──▶ transcribe ──▶ summarise ──▶ store ──▶ feed.xml
                (official      (yt-dlp +     (optional,   (sqlite)    │
                 channel RSS)   ffmpeg +      OpenAI-                 ▼
                                whisper.cpp)  compatible)         any reader
```

Each stage takes one input and returns one output, so each can be run and
inspected alone.

- **sources** — channel ID → list of `(video_id, url, title, published)`. Reads
  YouTube's official per-channel RSS. No API key, no scraping.
- **transcribe** — video URL → transcript text. Shells out to `yt-dlp`,
  `ffmpeg`, and `whisper-cli`. Returns `None` for a live or upcoming stream,
  which is different from returning empty: a stream becomes an ordinary
  recording once it ends and should be picked up then.
- **summarise** — text → summary. Optional. Posts to any OpenAI-compatible
  endpoint, so Ollama, vLLM, llama.cpp or a hosted API all work unchanged.
- **store** — SQLite, one file. Holds processed video IDs, transcripts and
  summaries. This is the only state; nothing is written into another
  application's database.
- **feed** — stored entries → Atom XML.

### What an entry contains

Entry content is the summary first, then the timestamped transcript. The summary
leads so a reader's list view shows something worth reading without any
per-reader configuration; the transcript follows so full-text search reaches the
whole video. Title, link, published date and thumbnail come from the channel
feed unchanged.

Timestamps stay in whisper's own `[00:12:34.000 --> 00:12:38.000]` form. Search
returns a whole entry rather than a position within it, so the timestamps are
what let the reader find the moment by eye. Reformatting them buys nothing.

### Configuration

One file. Channels; the whisper binary, model and device; the summarisation
endpoint, model and prompt, or nothing to disable it; output path and optional
listen port; per-run limits.

The whisper device is configuration, not detection. On the development machine
Vulkan device 0 is an integrated GPU and device 1 is the discrete card, and
picking wrong is not an error — just 22x slower (97s against 4.4s on the same
clip). Guessing on the user's behalf would hide that.

Language is not configured: `whisper-cli` defaults to English rather than
detecting, which silently mangles other languages instead of failing, so
`-l auto` is always passed.

### Failure handling

A video that fails is logged and left unrecorded, so the next run retries it.
There is no failure state to clear and no retry counter to tune. The process
exits non-zero only when there was work and none of it succeeded — a bad
endpoint, a missing binary, no network. One video failing to download is
ordinary operation and must not page anyone.

Live and upcoming streams are skipped by asking `yt-dlp` for `live_status`
first, a two-second metadata call. Without it, a live stream downloads until the
stream ends: one appeared during testing and would have consumed the entire
timeout every night while starving everything behind it.

Every external command carries a timeout.

## Hardware

whisper.cpp runs on CPU; a GPU makes it fast rather than possible. Measured on an
RTX 5090 via the Vulkan backend: 63-66x realtime, so an hour of video takes about
a minute, and a 4m36s clip transcribes in 4.4 seconds. CPU users should expect
roughly realtime and will want a smaller model.

The project ships no model. `whisper-cli`, `yt-dlp` and `ffmpeg` are the user's
to install, which keeps this a script rather than a platform.

## Testing

Unit tests cover the pure parts: parsing a channel feed, deciding live status
from `yt-dlp` output, rendering entries to Atom, and the store's
already-processed check. The stages that shell out are covered by one end-to-end
run against a real short video, documented rather than automated — mocking
`yt-dlp` would test the mock.

## Rejected alternatives

**Writing into a reader's database.** The first working version did this against
Karakeep: transcript into the `note` field, progress tracked with a tag. It
worked, and every problem it hit came from that coupling — the summariser never
reads `note`, the search API rejects a limit above 100, `summarizationStatus`
reports success for entries that have no summary, and the built-in summariser
calls Ollama's `/api/generate`, whose stream has no thinking/content split, so a
thinking model's reasoning was stored as the summary. A feed has none of these
failure modes because it does not know who reads it.

**A RSSHub route.** The right shape, wrong timing budget: a feed request cannot
wait 40 seconds per video.

**YouTube captions instead of whisper.** Measured above. Faster and free, but
wrong often enough to corrupt a summary, and rate-limited anyway.

**Handling sources other than YouTube.** Reddit, articles and anything else with
a real feed are already served by existing tools; Reddit specifically is better
read on Reddit. YouTube is the only source whose text does not exist yet.
